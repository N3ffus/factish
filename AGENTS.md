# Factish project rules

- Game content is every CSV listed in `CONTENT_FILES` in `backend/import_content.py`, imported together. Current list: `factish_100_facts_and_fakes.csv` (50 facts + 50 fakes), `factish_new_part01.csv` (200 + 200, ids 1-400), `factish_new_part02.csv` (200 + 200, ids 401-800), `factish_new_part03.csv` (200 + 200, ids 801-1200), and `factish_new_part04.csv` (250 + 250, ids 1201-1700), which gives 900 + 900 on prod since 2026-09-25. Do not use factual statements from the HTML design mockup. The 20000-row `factish_20000_facts_and_fakes.csv` was tried on 2026-09-23 and rolled back at the user's request; do not reintroduce it unless asked.
- New CSV files from the user are ADDED to the existing content, never swapped in for it (user correction, 2026-09-23: "надо добавлять новые, а не удалять старые"). Copy the file into `content/`, append it to `CONTENT_FILES`, and raise the expected counts in `tests/test_game.py`. `id` ranges of different files may overlap (the 100-row file and part01 both start at 1), so records are keyed by statement text; `source` (file name) + `source_id` only record where a row came from. The import rejects a statement repeated across files. Dropping a file from `CONTENT_FILES` deactivates its rows.
- Store facts and fakes in separate SQLite tables. Keep difficulty with each content record. Build every round by independently selecting one random fact and one random fake.

## Deployment (prod)

- Deploy over `ssh openclaw`; the app lives in `/home/clawadmin/apps/factish` (no git there, files are copied).
- Build the frontend locally with `FACTISH_BASE_PATH='/factish/'` (`npm run build` in `frontend`). Run it from PowerShell (or with `MSYS_NO_PATHCONV=1`): Git Bash rewrites `/factish/` to `C:/Program Files/Git/factish/` and the build silently gets a broken base path. Check that `dist/index.html` references `/factish/assets/...`. Before overwriting, compare remote vs local `md5sum` of backend/content/config files so remote-only edits are not lost.
- Back up to `/home/clawadmin/apps/factish-backup-<timestamp>`: the files being replaced (`backend`, `content`, `frontend/dist`) plus the database, copied with the SQLite backup API inside the container (`docker exec factish python -c "...sqlite3...backup..."` into `/app/data`, then move it out); do not `cp` the live WAL database.
- Upload changed files as one `.tgz` via `scp` and verify its `md5sum` on the server; a streamed `tar | ssh` of a multi-MB payload got reset by the server (`Connection reset by peer`). In Git Bash use `tar --force-local` or a `cygpath -u` path, since `C:` paths break tar.
- When content or migrations change, rehearse on a copy of the backed-up prod DB first: `scp` it locally, set `FACTISH_DATABASE_URL=sqlite:///<copy>`, then run `.venv/Scripts/alembic.exe upgrade head` and `.venv/Scripts/python.exe -m backend.import_content`. The container runs both on every start, so a failure there keeps it crashing. The prod DB keeps ~10k inactive rows from the rolled-back 20000-row import; a new statement that matches one of them reactivates that row. A content-only change needs no frontend rebuild: upload just `backend/import_content.py` and `content/<new>.csv`, then check `questionCount` in `/factish/api/bootstrap` instead of the asset hash.
- Then run `docker compose -f compose.prod.yml up -d --build`, wait for container health `healthy`, and check `docker logs factish` for the `Imported N facts and M fakes` line (the CSV import runs on every start).
- Verify at `https://neffus.ru/factish/` (new asset hash in HTML, `/factish/api/bootstrap` returns 200).
